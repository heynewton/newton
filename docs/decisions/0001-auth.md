# 0001: Supabase Auth, with the provider kept swappable

**Status:** Decided, 2026-10-18. **Issues:** #5, #27.

## Context

Newton needs sign-in from Phase 1, with each person linked to the boats they're a member of.
Postgres row-level security (RLS) enforces that link, so the database has to trust the sign-in
token. We want Google and Apple sign-in, and we don't want to be stuck if we ever move off
Supabase.

## Decision

Use Supabase Auth: email magic link first (#5), then Google and Apple (#27). Build #5 so the
provider can change later:

- `people.id` is Newton's own ID. The provider's user ID lives only in `people.auth_subject`,
  and nothing else refers to it.
- RLS policies call a `current_person_id()` SQL function instead of `auth.uid()`. Changing
  provider means rewriting that one function.
- `apps/web` reaches the database through one data-access module, not the Supabase client in
  components.

## Alternative considered: Auth0

Chosen to make a move off Supabase easier. Rejected for now:

- Auth is the smallest part of that move. The hard parts are the RLS-on-user-token model,
  Storage and the Supabase client calls, which Auth0 doesn't change (Supabase would still
  check Auth0 tokens as a third-party provider).
- Supabase Auth keeps users in our own Postgres. With magic links and social logins there are
  no passwords to migrate, so moving users later means importing email addresses.
- Auth0 adds a vendor, keys and a bill, and needs a cloud tenant even for local development
  and RLS tests. It is lock-in too, just to another company.
- Supabase Auth already supports Google and Apple, on the web and natively in Expo.

Revisit if we need what Supabase Auth doesn't do well, such as enterprise SSO for fleets
(Phase 4). The swappable design keeps that change about as cheap then as now.

## Consequences

- Apple sign-in needs a paid Apple Developer account, and its web client secret expires
  every 6 months, so someone has to renew it.
- An iOS app offering Google sign-in must also offer Sign in with Apple; we offer both.
- Apple's "Hide My Email" gives relay login addresses, so email-in (#10) matches senders against
  each person's verified sender addresses, not their login (#27).
